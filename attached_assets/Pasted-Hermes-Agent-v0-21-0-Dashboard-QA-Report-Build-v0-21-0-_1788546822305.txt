Two root causes account for most of the P0/P1 list:

/api/files has no valid default path → the whole Files page is dead.
Sessions are the source of truth for things that aren't sessions. The Models page builds one card per session instead of per model, and sessions are sorted by creation time (the session ID) while being labelled with last-activity timestamps. Fix the sort key and the grouping and five separate visible bugs disappear at once.


P0 — Blocking
1. Files page is completely unusable (500 on load, no recovery)
What happens: Navigating to Files immediately shows

Error: 500: {"detail":"Could not stat path: [Errno 2] No such file or directory:

'/nix/store/1h6gvvb0wksl4bkg75kzy9k8kmrgim8r-user-environment'"}

The file table is empty and the drop-zone is stuck on "Loading" forever. There is no path bar, no breadcrumb, no "go to workspace" — so once the default path fails there is no way to reach any file. Upload/Create are effectively dead too.

Verified at the API layer:

Request
Result
GET /api/files (no path)
500 — stats /nix/store/…-user-environment
GET /api/files?path=/home/runner/workspace
200, correct listing
GET /api/files?path=/nix/store/…-user-environment
404 Path not found


Root cause: the no-path branch resolves the default from the process environment (the Nix profile symlink — most likely Path(sys.executable).parents[1], os.environ["VIRTUAL_ENV"], or a which-resolved prefix) rather than from the agent workspace. That path exists at build time but not at runtime in this container.

Fix:

Default to the configured workspace, with a fallback chain:

DEFAULT_ROOTS = [cfg.workspace_dir, Path.home(), Path("/")]

root = next((p for p in DEFAULT_ROOTS if p and p.is_dir()), Path("/"))

/home/runner/workspace is already the correct value — it's what the chat banner prints and what /api/profiles returns as the profile path parent.

Return 404, not 500, for a missing path — a bad path is a client-visible condition, not a server fault. Only wrap genuinely unexpected OSError in a 500.
Add a path/breadcrumb bar to the Files UI so a failed default is recoverable, and render a real empty state instead of leaving the drop-zone on "Loading".
Clear the Loading state in the finally/catch branch of the fetch — right now it's only cleared on success.


2. Webhooks → "+ NEW SUBSCRIPTION" is a dead button
What happens: Clicking + NEW SUBSCRIPTION (top right) does nothing. No modal, no toast, no navigation, no console error. Clicked repeatedly — silent every time.

It appears to be gated on the webhook receiver being enabled ("Webhook receiver disabled" banner is showing), but the button is rendered in its normal enabled style and gives zero feedback.

Fix: Either

disable the button (disabled + aria-disabled + title="Enable the webhook receiver first" + dimmed styling) while receiver_enabled === false, or
open the modal anyway and show an inline "you'll need to enable the receiver before this fires" note.

Silently ignoring a click on a primary action is the worst of the three options. Add a click handler assertion in tests so a missing onClick fails CI.


3. Toasts render behind the modal backdrop and are unreadable
Reproduce: Cron → CREATE → click CREATE with an empty form. Also MCP → ADD SERVER → click ADD with an empty name.

The validation toast (PROMPT & SCHEDULE (CRON EXPRESSION) REQUIRED, NAME REQUIRED) appears in the top-right corner of the page, outside and beneath the modal overlay, dimmed by the backdrop and rendered dark-red-on-dark-green. A user clicking a button in the middle of a modal will never see it. It auto-dismisses in ~3s.

The contrast problem exists outside modals too: Channels → Discord Test shows DISCORD: DISCORD IS DISABLED. ENABLE IT, THEN RESTART THE GATEWAY. in the same barely-legible dark red.

Fix:

z-index: put the toast container in its own portal above the modal layer. Establish an explicit scale rather than ad-hoc values:

--z-modal-backdrop: 1000;

--z-modal: 1010;

--z-toast: 1100;

and make sure the toast portal is not a child of any element with a transform/filter/backdrop-filter (that creates a containing block and traps it under the backdrop regardless of z-index).

Contrast: the error toast needs to meet 4.5:1 against its own background, not against the page. Give it a solid surface (e.g. #2a0f12 bg / #ff8a8a text) instead of a translucent red on the dark-green ground.
Placement: for validation errors raised inside a modal, render the message inside the modal, next to the submit button — and mark the offending fields with aria-invalid.
The Cron message is also wrong: it demands "SCHEDULE (CRON EXPRESSION)" while the form is in Every interval mode with 30 minutes prefilled. Make the message match the active schedule mode, and only name the fields that are actually missing (here: prompt).

The page's own header says "6 MODELS USED / 9 TOTAL SESSIONS" — so the header is right and the cards are wrong. Each card shows its own "N sessions" count (gemini-3.8-flash is split into 2 + 1 + 2 across three cards).

Root cause — confirmed: there is no /api/models endpoint (404). The page derives cards from /api/sessions, which returns 10 sessions; one has model: null and is dropped → 9 cards. Grouping fails because model IDs are inconsistently namespaced in the session records:

google/gemini-3.8-flash    gemini-3.7-flash        ← bare

claude-opus-5              ← bare                  x-ai/grok-4.6

claude-sonnet-4-6          ← bare                  gemini-3.1-pro-preview  ← bare

Fix:

Normalise the model identifier at write time, not at render time. Store provider and model as separate columns and always write the canonical provider/model string; backfill existing session rows.
Group by that canonical key when building the grid: one card per distinct model, sessions = sum of the group.
Add a GET /api/models endpoint that does this aggregation server-side, so the count in the header and the cards can never disagree — they'd come from one query.
The #1…#9 rank numbers are currently arbitrary (not by session count: 1, 2, 3, 1, 1, 1, 2, 1, 1; not by recency either). Either sort by the metric the rank implies, or drop the numbers.

Also on this page: nous-provider cards (all three gemini-3.8-flash) show no context window, no in/out limits, and no Tools/Vision/Reasoning capability chips, while openrouter and anthropic cards show all of them. The model-metadata lookup has no entry for the nous provider. Add the metadata or fall back to the provider's /models endpoint rather than rendering a blank card.


5. Sessions are sorted by creation time but labelled with last-activity time
What happens: In Sessions → All → History, ordering reads:

1m ago · 3h · 3h · 3h · 4h · 4h · 4h · 5h · 1h ago (!) · yesterday

                                              ^^^^^^^ out of order

gev-youtube-50834a0dee0b70dd3f42 is 1h old but sits 9th, below sessions that are 4 and 5 hours old.

Root cause — confirmed: /api/sessions returns rows ordered by session id, and the ID is the creation timestamp (20260903_174930_4675b8). That session was created on Sept 3 but last used an hour ago. The list sorts on id while the UI renders updated_at.

Fix: sort on the same field you display.

-- was: ORDER BY id DESC

ORDER BY COALESCE(updated_at, last_message_at, created_at) DESC

Add an index on that column, and add a regression test asserting the returned updated_at sequence is monotonically decreasing.


6. Sessions "Overview" hides the newest session and caps silently at 5
What happens: Immediately after sending a chat message, the new session appears in History ("Respond with PING_OKll · 1m ago") but not in the Overview tab, whose top entry is 3h old. Overview also shows only 5 of 10 sessions with no pagination, no "show all", and no indication that it's truncated — while the stat bar above it says "10 Total".

The Chat page's own right-hand session list disagrees with both (it leads with a 1h-old session).

Fix:

Apply the same updated_at sort as #5 so the newest session leads.
Either label the panel honestly ("5 most recent") with a View all → link to History, or drop the cap.
Invalidate/refetch the sessions query when a chat turn completes so Overview and the Chat sidebar can't drift. One cache key for session lists across all three surfaces.


7. Profile reports 58 skills; Skills page and the agent both say 53
Verified at the API layer:

Two independent counters. The profile's is off by 5 — most likely it counts skill directories on disk (including hidden/invalid/template dirs, or plugin-provided skills) while /api/skills counts successfully-loaded manifests.

Fix: derive skill_count from the same registry /api/skills reads, i.e. len(registry.list_skills(profile)). If the 5 extra are real-but-unloadable skills, that's a separate bug worth surfacing — log which 5 fail to load rather than silently inflating a count.


8. Sidebar "Gateway Status" and "Active Sessions" drift from reality
Gateway Status: Off is correct (gateway_running: false), but during an active chat turn the chat footer showed "2 sessions" while the sidebar showed "Active Sessions: 0", then 1, then back to 0 after the turn. Different polling intervals against different endpoints.

Fix: single /api/status poll feeding both surfaces (it already returns active_sessions and gateway_running); push updates over the existing WebSocket instead of polling, so the two can't disagree mid-turn.


P2 — Usability & correctness
9. Chat input retains stale text across navigation, and Ctrl+A doesn't clear it
Returning to Chat after visiting Files left ll sitting in the prompt from a prior session. Ctrl+A followed by Backspace did not clear it — my typed message was inserted before the residue and sent as Reply with exactly: PING_OKll. Clicking in the input did not reposition the cursor either.

The /help output documents Ctrl+A as home (start of line) rather than select-all, so this is partly by design — but then:

Fix: the terminal-style input needs a documented, discoverable "clear draft" affordance. Ctrl+C and Esc Esc are listed in /help but nothing in the UI says so. Add a small ✕ in the input, and don't restore a draft that was never submitted after a full page navigation (or restore it visibly, with a "restored draft" hint).
10. SQLite handle leak — 5 writer connections to one DB in one process
From errors.log:

WARNING hermes_state: 5 live SessionDB handles on /home/runner/workspace/.hermes/state.db

in this process; each holds its own writer connection (read connections are capped at 8

for the file). A long-lived process should share one handle per path.

The code is already warning about its own bug. With a cap of 8, three more handles and session reads/writes start failing — which is a plausible contributor to #6 and #8.

Fix: a process-wide SessionDB registry keyed by resolved path, handed out by a factory. Turn the warning into a hard error in tests so a new leak fails CI rather than logging.
11. Event loop stalls of 5–13 seconds
WARNING hermes_cli.web_server: event loop stalled 5.3s (GIL pressure suspected)

… 7.5s … 5.4s … 5.4s … 9.9s … 13.1s

Six stalls in a ~10-minute window. A trivial chat turn ("Reply with exactly: PING_OK") took 22s end to end against a flash model. The PTY WebSocket also dropped twice during testing (code=4409, code=1006).

Fix: find the synchronous work on the event loop and move it to run_in_executor / a worker process — the prime suspects are the SQLite writes above (sync sqlite3 on the loop thread), config/YAML parsing on every request, and skill-manifest scanning. Instrument with loop.set_debug(True) + slow_callback_duration to name the callback rather than guessing.
12. Log spam: one warning per tool, per turn
Every single turn emits a warning for each gated tool:

WARNING tools.registry: check_fn check_browser_back_requirements returned False; …

… check_browser_cdp_check … check_browser_click_requirements … (×14 browser tools)

WARNING tools.registry: check_fn _check_kanban_mode returned False; …   ← twice, identical

This is normal operation (browser toolset not configured), not a warning condition, and it buries the real errors in errors.log.

Fix: demote to DEBUG, and aggregate per toolset: INFO tools.registry: browser toolset unavailable (16 tools gated): cloud_provider not configured — one line, once, per toolset, per turn. Also de-duplicate the doubled _check_kanban_mode call.
13. OpenRouter credit failures never surface in the UI
errors.log shows repeated hard failures that the dashboard never mentioned:

ERROR agent.conversation_loop: Non-retryable client error: Error code: 402 —

'weight_exceeds_budget' … 'This request's maximum cost exceeds your available credits.

Add credits, or lower max_tokens' … model=x-ai/grok-4.6

Fix: surface non-retryable provider errors (402/401/429) as a persistent banner on Models and in the chat transcript, with the provider's own remedy_hint (OpenRouter returns a credits URL). A billing failure that only appears in a log file is a support ticket waiting to happen.
14. Sessions tab controls are inconsistent between tabs
Chats and All tabs show an Overview | History toggle but no search box.
Automation tab shows a search box but no Overview/History toggle.
The stat bar (10 Total / 10 Active / 0 Archived / 1304 Messages / 2 Sources) does not respond to the active filter — Automation shows "No sessions in this filter" while the bar still reads 10 Total.

Fix: one consistent control row across all three tabs (search + view toggle), and recompute the stat bar from the filtered set (or label it "All sessions" so it's clearly global).
15. Profile → "MANAGE SKILLS & TOOLS" isn't profile-scoped
Selecting it from the default profile's ⋮ menu navigates to the global Skills page with no profile context, no breadcrumb, and no way back. If profiles can have different skill sets (the profile card implies they can — it shows a per-profile count), this menu item doesn't do what it says.

Fix: either scope the page (/skills?profile=default with a "Managing skills for default" header and a back link), or rename the menu item to "Open skills" if skills are genuinely global.


P3 — Cosmetic & copy
16. Inline <code> renders with a blue selection-coloured background
On Channels (hermes gateway start, /home/runner/workspace/.hermes/.env) and MCP (every catalog endpoint URL), inline code renders on a bright blue background that looks exactly like an accidental text selection and clashes with the cream/teal terminal palette. Contrast is poor.

Fix: the code/kbd rule is falling through to a browser default or a stray ::selection colour. Give it a theme token — e.g. background: rgba(230,214,180,0.10); color: var(--accent-cream); border-radius: 3px; padding: 0 .3em.
17. Serif font leaking into a monospace UI
Session titles, preview text, modal titles ("NEW CRON JOB", "ADD MCP SERVER"), and helper text ("Sends as", "Selected skills are loaded before the prompt runs…") render in a serif face while everything around them is monospace. Consistent across Sessions, Cron, MCP, Plugins, Channels.

Fix: a font in the stack is failing to load and falling through to the generic serif default. Audit font-family declarations — every stack should end in monospace, never a bare family name. Check the @font-face sources actually resolve (and that they're not blocked by the CSP).
18. /help output has duplicate headings and broken column alignment
Two separate TUI section headers in one help listing. Descriptions collide with their usage strings when the usage is long:

/details [hidden|collapsed|expanded|cycle]set global agent detail visibility mode

Shift+Enter / Alt+Enterinsert newline

Fix: compute the description column from max(len(cmd + usage)) across all rows, with a minimum 2-space gutter; wrap descriptions rather than letting them run into the next column. Merge the two TUI groups.
19. Cron empty state points the wrong direction
"No cron jobs configured. Create one above." — the CREATE button is directly below that sentence (there's a second one in the top-right header). Say "Create one below", or just drop the direction since the button is right there.
20. Channels banner references a button that isn't where it says
"…then start the gateway with hermes gateway start (or the Restart button above)." The Restart Gateway control is in the left sidebar, not above the banner.

Fix: "…or use Restart Gateway in the sidebar."
21. Assorted small items
Cron → Blueprints: "Set up" buttons wrap to two lines (Set / up) on cards with longer descriptions. Add white-space: nowrap and a min-width.
Cron modal: the two-column grid breaks in Advanced Fields — BASE URL OVERRIDE spans full width, then SCRIPT is placed in the right column of the next row with the no_agent checkbox stranded to its left. Give each field an explicit grid-column.
Sessions: "1 tools" — pluralise (1 tool).
Modals: neither the Cron nor the MCP modal has a Cancel button, only the ×. Add one next to the primary action.
Skills: searching hides the entire CATEGORIES panel and the Learn a skill / + New skill buttons. Keep the chrome stable during search.
Config: every field's label restates its heading verbatim (FALLBACK PROVIDERS → "Fallback Providers", TOOLSETS → "Toolsets"). Drop the redundant label or use it for real help text.
Config: MAX CONCURRENT SESSIONS is blank with no placeholder — add placeholder="unlimited" so empty ≠ broken.
Config: 8 sections (Database, Desktop, Gateway, Loops, Lsp, Matrix, Mattermost, Logging) share one generic document icon while the rest have distinct ones.
Pairing: an entirely empty page — two empty lists, no explanation of what pairing is, no primary action, no docs link. Add an empty state that explains the feature and how a pairing request is initiated.
Plugins / MCP: a 30-plugin list and a 65-server catalog with no search or filter. Both need one; Skills and Config already have search, so the component exists.


What I'd fix first
#1 Files default path — one page is 100% dead; the fix is a three-line fallback chain.
#4 + #5 model grouping and session sort — one canonical model key and one ORDER BY clause clear four of the five P1 data bugs.
#3 toast z-index and contrast — every modal in the app currently swallows its own validation errors.
#10 + #11 DB handle leak and event-loop stalls — these are the ones that turn into intermittent, hard-to-reproduce failures under load, and the code is already warning about the first one.
